## Baseline findings

The project already contained a substantial desktop client: authenticated UDP transport, character selection/creation, DAT-rendered avatars and attachments, predicted movement with world collision, terrain/interior streaming, portal loading, retail UI/inventory/options, and server-backed combat. The controller owns movement; enabling a second pawn movement implementation would have conflicted with it.

There was no functioning VR rig, controller-driven arm pose, world-space retail UI, wrist menu, or physical combat protocol. Existing XR axis entries alone did not implement these features. The desktop spring arm, mouse camera, loading-screen view targets, and portal FOV transition would have interfered with headset camera ownership.

ACE's original combat requests select targets. Its missile collision helper intentionally rejects creatures other than the selected target. Sending a hand direction only from the client would therefore have left arrows unable to hit arbitrary creatures. The user authorized extending this included server.

## Implemented changes

- **OpenXR rig:** `ACEVRComponent` is attached to the existing pawn. It owns the HMD camera, grip/aim controller poses, input, tracking origin, world panels, fade, and visual helpers. The tracking origin has independent world rotation/location. Snap turns pivot around the HMD; room movement feeds existing collision prediction and compensates the tracking space by actual capsule movement.
- **Avatar:** existing human DAT parts receive a two-bone arm solution and controller hand poses. The local head is hidden to prevent viewing its interior. Body visibility is configurable; nonhuman/missing-arm appearances receive visible fallback arms and palms. Held-item attachment roots follow the selected hands.
- **Input/UI:** Touch mappings exist before OpenXR initializes its actions. Inventory/settings are controller-toggleable, with world-space login, character screens, and retail gameplay UI. Two pointers share a virtual Slate user so either hand can focus a text field and use the virtual keyboard. The keyboard supports shifted punctuation. Vendor, container, and trade responses reveal the panel. Nearby use/pickup bypasses the desktop walking approach.
- **Spells:** the left wrist presents the active spell bank and explicit selection. Trigger presses sample the weapon aim pose. Server casts reuse ACE validation, costs, gestures, release, and recoil. Projectile origins/directions use the submitted hand pose; collision and damage stay in ACE. Non-projectile spells retain normal target semantics.
- **Melee:** tracking-space weapon sweeps reject locomotion, discontinuities, and repeated hits during one swing. The server validates finite bounded sweeps against authoritative target position and reach, enforces timing/equipment, and invokes existing damage/stamina/proc behavior.
- **Missiles:** two-hand bow nock/draw/release, crossbow load/trigger, and basic thrown release send hand trajectories. Only explicitly marked VR projectiles acquire the creature physically hit. The damage calculation snapshots missile accuracy/attack skill for these projectiles. Ammo consumption precedes reload so a final arrow is not reattached.
- **Transitions/settings:** tracking/focus loss and menu/world state changes cancel gestures. VR owns the camera during desktop loading/reveal flows. Per-user settings are clamped and persisted independently of character options. The build enables OpenXR and instanced stereo, and cooks fallback geometry.

## Protocol and authority

The authenticated game action `0xF7D0` carries private version 1. A version/kind-0 hello is exactly eight bytes. The server replies with game event `0xF7D0`, version 1 and feature flags 15 (combat bits 7 plus optional world snapshot bit 8). Capabilities reset on disconnect/world reset. Physical attacks are gated on this acknowledgment.

Combat actions are exactly 64 bytes: eight little-endian 32-bit integers (version, kind, sequence, cell, teleport epoch, weapon, spell/subject, target), followed by eight floats (origin XYZ, direction or sweep endpoint XYZ, amount, duration). Coordinates use AC world axes in meters relative to player feet. Kind 1 casts, kind 2 submits a melee sweep, and kind 3 releases a missile.

The server rejects malformed lengths, unsupported versions/kinds, nonfinite values, implausible reach/direction/sweep speed, replayed sequence numbers, stale cell/teleport epochs, invalid equipment, and disallowed player state. It retains authority over spells, resources, ammo, cooldowns, target legality, and damage. Hand poses themselves are client input; this is bounded validation, not proof of physical controller motion. Competitive use needs a separate abuse/latency review and tuning.

Projectile routing is deliberately opt-in. Existing desktop missile collision retains its selected-target rule. Existing spell calls keep their original behavior when no VR aim is attached to the current cast. Ordinary server clients do not need the new protocol.
