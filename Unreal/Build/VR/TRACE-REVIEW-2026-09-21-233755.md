## First implementation priorities

### 1. Cache the UI name index until the element tree changes

`ACE_UINameIndex` takes **346 µs every gameplay frame**, with 883 calls and a maximum of 477 µs. This is about 3.4% of the measured average frame. It is the clearest recurring shared-code opportunity with no intended visual quality tradeoff.

`UACEUIElementManager::BeginNameLookupPass` and `EndNameLookupPass` invalidate the map unconditionally. `BuildNameLookupIndex` then walks the entire element tree and repopulates name buckets. The first lookup in `RefreshVitalsOverlays` triggers the rebuild; this does not mean drawing the health bars themselves costs all that time.

Use a tree-generation counter and invalidate on actual add/remove/rename operations. Keep visibility checks at lookup time. Route direct `Children` mutations through invalidation-aware helpers before keeping the index across frames. Simply deleting the invalidation calls would recreate stale references and incorrect window selection.

Sources: [ACEUIElementManager.cpp](../../Plugins/ACEClient/Source/ACEClient/Private/UI/ACEUIElementManager.cpp), `BeginNameLookupPass` at line 476, `BuildNameLookupIndex` at line 497; [ACEUIGameplayBinder.cpp](../../Plugins/ACEClient/Source/ACEClient/Private/UI/ACEUIGameplayBinder.cpp), lookup pass at line 673. Existing lookup lifecycle coverage is in `Private/Tests/ACEVRInputLifecycleTests.cpp`.

### 2. Split visibility topology from camera-dependent visibility

`ACE_Visibility` consumes approximately **442 µs self / 443 µs inclusive per frame**, with calls reaching 940 µs in the gameplay interval. The first reveal also contains a 4.98 ms visibility call.

`UpdateCameraVisibility` invokes `UpdateOutdoorEnvCellDraw`, rebuilds the admitted landblock-key array, gathers portals, walks environment cells, reapplies portal/ceiling/shadow settings, walks terrain actors, and calls `RefreshCellVisibility` across world entities and their attachment chains.

Cache landblock/portal topology until residency changes; reuse temporary containers; apply cell/material/actor state only when it changes. Preserve per-frame camera/frustum evaluation and immediately update moved/new entities. Do not solve this by disabling culling or lowering its frequency indiscriminately: doorway visibility and stereo edge popping have already required correctness fixes.

Sources: [ACETerrainPresenterComponent.cpp](../../Plugins/ACEClient/Source/ACEClient/Private/ACETerrainPresenterComponent.cpp), `UpdateCameraVisibility` at 3146 and `UpdateOutdoorEnvCellDraw` at 3690; [ACEWorldPresenterComponent.cpp](../../Plugins/ACEClient/Source/ACEClient/Private/ACEWorldPresenterComponent.cpp), `RefreshCellVisibility` at 194.

The **combined current index and visibility cost is about 0.79 ms/frame**. That is the amount of work to attack, not a promise to recover all of it or an additive FPS forecast.

### 3. Make one character appearance interruptible

Across the capture, **132 appearance calls take 1.299 seconds inclusive**, averaging 9.84 ms and reaching **69.04 ms** for one call. During entry, appearances consume approximately **605 ms in process second 367** and **501 ms in second 368**. The worst appearance is inside an 82.13 ms frame. Later gameplay still includes a 31.34 ms appearance call.

`ApplyWorldObject` synchronously builds the setup appearance, creates/registers part components, applies mesh sections/materials, and creates world-lighting instances. The matching log reports humanoid examples with roughly 10–18 ms of decode/component setup followed by 12–22 ms of mesh/material work; editor shader preparation contributes to some cases. The trace's broad appearance scope cannot independently attribute every substep.

The queue already has 2 ms portal / 4 ms world deadlines, but checks them **between complete appearances** and always permits one item. A single 69 ms item defeats that budget. Move plain DAT geometry/texture preparation to workers and commit components/sections in bounded batches, with cancellation and appearance-version checks. Preserve a coherent old appearance until its replacement is ready. Additional subscopes should separate decode, component registration, mesh application, and lighting instances.

Sources: [ACECharacterAppearanceComponent.cpp](../../Plugins/ACEClient/Source/ACEClient/Private/ACECharacterAppearanceComponent.cpp), `ApplyWorldObject` at 529 and synchronous `BuildSetupAppearance`/`ApplySetupParts`; [ACEWorldPresenterComponent.cpp](../../Plugins/ACEClient/Source/ACEClient/Private/ACEWorldPresenterComponent.cpp), `DrainPendingDatAppearance`.

### 4. Stop recomputing expensive terrain compression after disk-cache hits

**175 `ACE_PrepareLandMips` calls consume 9.499 CPU-seconds across background workers**, averaging 54.28 ms each, maximum 68.94 ms. Inside these scopes, **1,925 `FCompression::CompressMemory` calls consume 8.741 CPU-seconds**: 11 mip levels per texture. These overlapping worker times must not be described as 9.5 seconds of frozen game thread.

Source inspection explains the cost: `PrepareUploadMips` calls `FCompression::CompressMemory(NAME_LZ4, ...)` without speed flags. UE 5.8's `Core/Private/Misc/Compression.cpp` dispatches that to **`LZ4_compress_HC` at the default HC level**, not the fast LZ4 encoder. `COMPRESS_BiasSpeed` selects the minimum HC level; it still uses HC.

The disk PCode cache stores a zlib-compressed base image. `FillSectionBake` calls `PrepareUploadMips` even after a successful disk-cache read, repeating filtering, channel shuffle, and HC compression on a fresh app/session cache. Benchmark the minimum HC level or a supported fast lossless encoder, recording both speed and retained byte size. Extend the versioned disk cache to store prepared mips and their integrity/fingerprint information. Keep existing DAT resolution, alpha, color space, seam blending, and mip filtering unchanged.

The game-thread side is also measurable: **175 `ACE_UploadLandMips` calls take 707.3 ms inclusive**, averaging **4.04 ms**, maximum **5.22 ms**. This scope prepares/decompresses RHI upload allocations; it does not measure the GPU's transfer duration. In one 64.62 ms frame, it accounts for roughly **48.0 ms including its decompression children**. Queue prepared upload payloads with a strict memory cap and drain by elapsed time; avoid committing many new terrain textures in one frame.

Sources: [ACETerrainBlendCache.cpp](../../Plugins/ACEClient/Source/ACEClient/Private/Dat/ACETerrainBlendCache.cpp), `PrepareUploadMips` and `CopyMip`; [ACELandTextureMipProvider.cpp](../../Plugins/ACEClient/Source/ACEClient/Private/Dat/ACELandTextureMipProvider.cpp), `GetInitialMipData`; [ACELandblockMeshBuilder.cpp](../../Plugins/ACEClient/Source/ACEClient/Private/Dat/ACELandblockMeshBuilder.cpp), `FillSectionBake` at 1047; [ACEPCodeTileCache.cpp](../../Plugins/ACEClient/Source/ACEClient/Private/Dat/ACEPCodeTileCache.cpp).

## Other recurring costs worth measuring

- **Animation:** 62,685 calls in the aligned gameplay interval; about **2.79 µs self per call**, **0.198 ms self per frame / 0.316 ms inclusive per frame**. Existing distance throttling already exists. Optimize repeated evaluations of identical idle poses or unchanged transforms before reducing nearby animation quality.
- **Rigid part updates:** 507,789 `ACEPart` scopes, approximately **0.32 µs self per call**, accumulating **0.183 ms/frame**. Parent scopes show transform/animation and deferred render updates, not simply unnecessary component ticks. Batch changed transforms and preserve the current cached-draw path. This is a small recurring target, not the main bottleneck.
- **Player controller:** about **0.336 ms self/frame**, but the current broad scope does not identify a single removable operation. Add subscopes around movement, selection, input, and UI-scale application before changing behavior.
- **Radar / shortcut / chat chrome refreshes:** approximately **52 / 37 / 35 µs per frame**, respectively. Cache static chrome/layout; refresh values and geometry when their inputs change. Avoid broad blanket throttling of combat, chat, and pointer feedback.
- **Effects:** about **71 µs self/frame**, 128 µs inclusive/frame in this interval. It does not contain a representative heavy spell battle, so it cannot clear particles as a combat bottleneck.
- **Network and remote presentation:** individual aggregate scope costs are only around **30–31 µs/frame** in the 378–387-second window. Do not lower network update rates based on this capture.
- **Fog:** `ACE_SkyFog` is about **2 µs per update**, 85 updates / 0.170 ms total in that window. It is no longer a significant hotspot in this desktop trace. This supports the new shared-fog design, but is not a same-device before/after Quest FPS measurement.

The sub-microsecond part estimates are aggregates over many calls. Event CSV timestamps are rounded to microseconds, so individual tiny event durations should not be treated as precise benchmarks.

## Editor overhead and GPU candidates

### Editor UI substantially affects this result

In the 378–387-second interval:

- `Slate::Prepass`: **2.015 ms inclusive / 1.735 ms self per call**, once per frame.
- Two `Slate_PaintSlowPath` window branches per frame: the branch containing the gameplay HUD averages **1.002 ms inclusive**; the other window branch averages **1.597 ms**.
- `ProcessLocalPlayerSlateOperations`: **1.229 ms/call**. Engine source generates a path to each game viewport before processing local-player replies. Add subscopes or compare packaged behavior before attributing this whole cost to our input code.
- Editor details-panel tick alone averages **278 µs/frame**.

The HUD index cost is nested inside gameplay painting. Prepass, paint, HUD, and child scopes must not all be added as independent savings. First compare the packaged desktop client at the same view, resolution, settings, and uncapped frame rate. Editor overhead cannot simply be subtracted to promise a packaged FPS result.

### Temporal Super Resolution is the main GPU experiment to run

In the gameplay interval, the GPU TSR scopes average approximately **4.534 ms on the compute queue** and **0.884 ms on graphics**. These overlap and must not be added. The enclosing `SceneRender` spans average approximately **6.65–6.71 ms per queue**. Graphics shadow depth averages **0.292 ms**, base pass **0.243 ms**, and prepass **0.169 ms**.

TSR is therefore the strongest desktop GPU candidate for an A/B test: capture packaged gameplay with current TSR, then a lower TSR quality tier or another supported AA method at the same output/internal resolution. Evaluate tree silhouettes, roads, text, and movement before adopting a change. Do not disable anti-aliasing or reduce shadows blindly. This deferred desktop TSR finding does not apply directly to native Quest's mobile rendering path.

The GPU analyzer reported 101 interleaved events (maximum correction ~0.265 ms), 88 interleaved/reversed events (~0.259 ms), and five negative durations (~0.051 ms). Queue scopes can also span dependency waits. Treat the measured TSR scope as a strong lead, not proof that every millisecond is recoverable shader execution. Confirm with a focused GPU profile before claiming savings from tiny passes.

### Separate editor shader work from shipped loading work

The capture has runtime material compilation and global render-state recreation inside some 67–128 ms entry/reveal frames. `PrepareRuntimeMaterials` intentionally bypasses its packaged preload path under `WITH_EDITORONLY_DATA`, and the log shows runtime material creation. Packaged assets already use a different preloaded path. Improving PIE material reuse would make testing smoother, but do not count all these editor stalls as Quest regressions.

The largest ~327–338 ms frames occur **after `EndPlayMap`**, predominantly in `FEngineLoop_UpdateTimeAndHandleMaxTickRate`. They are editor pacing after stopping play, not in-world loading stalls. A 235 ms earlier frame is predominantly editor Slate/text prepass work.

## Misleading totals and missing measurements

- `WaitForTasks` totals 78.0 seconds across threads; `IDXGIOutput::WaitForVBlank_NoBusyWait` totals 50.1 seconds. Wait scopes are synchronization/pacing and overlap other work. They are not 128 seconds of removable CPU computation.
- File-system iteration totals 27.60 seconds, almost entirely on **`FileSystemCacheStoreMaintainer`**, Unreal's background derived-data-cache maintenance. The game-thread portion is only **1.12 ms total**. It may contend for I/O, but is not a demonstrated 27-second game stall; do not rewrite DAT loading or delete caches based on this aggregate.
- Memory counters are named in the trace but export no meaningful RAM/VRAM samples. Selected draw/widget counters contain only zero reset samples. These do **not** mean zero memory or zero draws. This recording cannot establish peak RAM, GPU texture allocation, or a memory leak.
- CPU scopes report elapsed wall time while active, not OS-scheduled CPU occupancy. A sampled/context-switch trace would be needed to prove time lost to preemption inside a scope.
- The 21.8 million instrumented CPU scopes in 50 seconds add profiling overhead, especially for extremely small operations. Verify improvements with the same trace channels and with tracing disabled.

## Validation order

1. Capture packaged desktop at the same scene; separate editor-only costs from shared runtime costs. Include a 30–60-second steady view and a separately marked first-login segment.
2. Implement generation-based UI indexing and visibility state/topology reuse individually. Compare the named scopes before/after; run UI mutation, duplicate-name/visibility, portal transition, and stereo culling regressions.
3. Benchmark lossless terrain encoders on actual cached tiles, then persist prepared mips. Measure worker time, first upload latency, retained RAM, byte-identical mip output, and cold/warm portal frame percentiles.
4. Split appearance preparation and commits. Measure the maximum atomic step, not just average queue time. Test cancellation during teleport/logout and equipment changes.
5. Run the desktop TSR comparison with image-quality checks. Repeat shared-code changes on native Quest with valid CPU/GPU and resident-memory counters. Do not translate RTX 5090 measurements into predicted Quest savings.
